## Comportamiento implementado

- FastAPI recibe `Authorization: Bearer <access_token>` y verifica el usuario mediante `GET /auth/v1/user` del proyecto configurado. No decodifica JWT sin validación ni utiliza identidades demo.
- Lee el perfil propio de `perfiles`, traduciendo `nombre_completo`/`biografia` a los nombres que consumen las rutas existentes. Esta adaptación no migra el módulo completo de perfiles.
- El catálogo consulta `public.capabilities` mediante PostgREST con la clave pública del proyecto y el token de cada usuario. No usa service_role ni conserva estado del catálogo en memoria.
- Cada lectura aplica `visible_to(None, user_id)` en origen y `visible_to(rows, user_id)` a los resultados. Además de este control, Supabase debe tener RLS y grants correctos.
- Consultar, editar, eliminar o clonar una capacidad privada ajena responde 404. Editar/eliminar una pública ajena también responde 404.
- Crear asigna un UUID completo y el propietario autenticado. El cliente no puede suministrar propietario, identificador ni contadores.
- Crear y clonar generan borradores. La API rechaza `status=published` con 409, pendiente del futuro contrato de versiones/pruebas/habilitación. Editar devuelve a borrador.
- Clonar preserva `cloned_from`, crea una copia privada y no modifica al autor original. El contador de clones queda pendiente de una operación transaccional revisada; no se incrementa con una actualización insegura.
- UI: listas propias/comunidad, paginación real y clonación mediante `src/api.js`. Sin fallback a catálogo mock. Los filtros de texto/categoría de la UI operan sobre las filas cargadas y lo indican.
- El botón de ejecución informa que falta integrar el motor. El formulario/laboratorio de creación sigue asignado a Fahida; no se implementó aquí.

## Configuración local

1. Copiar `backend/.env.example` a `backend/.env` si este último no existe. No sobrescribir configuraciones existentes.
2. Configurar `SUPABASE_URL` y `SUPABASE_ANON_KEY` con la URL y clave publishable/anon del mismo proyecto del frontend. No utilizar service_role ni el secreto de firma JWT. No compartir tokens en el chat.
3. Mantener el `.env` del frontend con su URL y clave pública correspondientes y `VITE_API_URL=http://127.0.0.1:8000/api`.
4. Instalar dependencias y ejecutar la API como indica README. La API carga siempre `backend/.env`, independientemente de la carpeta desde la que se invoque.

En esta sesión se creó un entorno `.venv/` en la raíz (ignorado por Git). Comandos desde la raíz en Windows:

```powershell
.\.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
.\.venv\Scripts\python.exe scripts/supabase/setup_env.py
.\.venv\Scripts\python.exe scripts/supabase/check_catalog.py
Set-Location backend
..\.venv\Scripts\python.exe main.py
```

Sin configuración, las peticiones autenticadas responden 503 y las que no tienen token responden 401. Caídas del proveedor no se presentan como sesión expirada. No se exponen los mensajes SQL ni cuerpos de error del proveedor.

## Contrato para Fahida

Todas las rutas de catálogo requieren token. La respuesta mantiene `{success, message, data, timestamp}` y los errores `{detail}`.

| Operación | Ruta | Resultado |
| --- | --- | --- |
| Listar | `GET /api/capabilities?scope=mine\|community\|available&limit=20&cursor=UUID` | `data: {items, next_cursor}`; orden estable por UUID ascendente. |
| Buscar | Misma ruta con `q`, `type` y/o `owner` | Búsqueda textual, sin afirmar semántica. |
| Similares | `GET /api/capabilities/similar?name=...` | `data: {items, next_cursor}`; coincidencia textual por nombre propuesto. `description` se conserva por compatibilidad pero no se usa todavía. |
| Detalle | `GET /api/capabilities/{uuid}` | Fila visible. |
| Crear | `POST /api/capabilities` | Borrador persistido por Supabase, HTTP 201. |
| Editar | `PUT /api/capabilities/{uuid}` | Solo campos enviados, propietario verificado, estado draft. |
| Clonar | `POST /api/capabilities/{uuid}/clone` | Copia propia privada, HTTP 201. |
| Eliminar | `DELETE /api/capabilities/{uuid}` | `data: {deleted_id}`. |

Campos mínimos para crear: `name`, `description`, `input_type`, `output_type`. Tipos: `pdf`, `texto`, `imagen`, `audio`, `datos`. Visibilidad por defecto privada. No se admiten campos extra; no se aceptan null en campos obligatorios al actualizar. `owner_username` puede ser null si el perfil no tiene username.

La dependencia común `get_current_user` devuelve el UUID de Auth y los campos de presentación del perfil; ya no devuelve una referencia mutable al almacén demo. **No persistir cambios mutando ese diccionario.**
